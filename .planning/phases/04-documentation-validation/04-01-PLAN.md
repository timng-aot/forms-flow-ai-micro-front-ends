2. Quick Start section with three 3-line task entries (per user decision: "common tasks in 3 lines each"):
   - "How to add a new token": (1) Add to core.json or semantic.json in DTCG format, (2) Run `npm run build:tokens`, (3) Import updated JSON to Figma via Token Studio
   - "How to rebuild CSS after token changes": (1) cd forms-flow-theme, (2) npm run build:tokens, (3) Output in tokens/dist/
   - "How to import tokens to Figma": (1) Open Figma → Plugins → Token Studio, (2) Import → Select tokens/core.json, (3) Repeat for tokens/semantic.json

**methodology.md** — Developer-facing methodology and maintenance guide.

Structure:
1. Title and overview paragraph explaining purpose: extraction methodology from SCSS to DTCG, naming conventions, and pipeline maintenance
2. Target audience: "Developers maintaining the design system"
3. "Why Design Tokens?" section (brief, 4 bullet points: single source of truth, design-dev sync, theme switching, consistency)
4. Architecture Decisions section with three subsections (per user decision: WHY behind decisions):
   - "Why W3C DTCG Format?" — Industry standard (Oct 2025 stable), tool compatibility (Token Studio, Style Dictionary), future-proof W3C standard
   - "Why Two Files (core.json + semantic.json)?" — Mirrors design thinking (primitives vs semantic), enables theme switching, matches Figma structure. Include SCSS → DTCG transformation example showing $indigo-100 from v8-scss/_theme.scss becoming ff.color.indigo-100 in core.json and color.action.primary in semantic.json (per user decision: SCSS source → DTCG token only, skip CSS output side)
   - "Why --ff- Prefix?" — Namespaces tokens, identifies source (Forms Flow), follows existing convention. Configured via custom name transform in Style Dictionary.
5. Token Pipeline section with 3 stages:
   - Stage 1: Extraction (Python scripts parse SCSS → DTCG JSON). Reference scripts/ directory.
   - Stage 2: Pre-computation (blend-with-white-to-hex resolved to hex). Reference tokens/scripts/precompute-colors.js
   - Stage 3: CSS Generation (Style Dictionary transforms DTCG → CSS custom properties). Reference npm run build:tokens
6. Extraction Examples section (per user decision: show SCSS source → DTCG token only):
   - Example 1: Color palette extraction (blend-with-white-to-hex pre-computed to hex values). Use real values from core.json.
   - Example 2: Spacing with semantic references (core numeric scale → semantic reference)
   - Example 3: Shadow CSS string → DTCG object conversion
7. Naming Conventions section (covers DOCS-02 requirement):
   - General rules: kebab-case, no dots/braces/dollars in names, dot notation via JSON nesting
   - ff- prefix via top-level group in core.json
   - Bootstrap semantic names preserved (primary, secondary, success, danger)
   - Per-category naming table with rules from dtcg-spec.md:
     - Color: ff.color.{hue}-{shade} (100-900 numeric scale)
     - Spacing: ff.spacing.{zero-padded-numeric} (025, 050, 100, etc.)
     - Typography: ff.font-size.{value}, ff.font-weight.{name}, ff.font-family.{name}
     - Border radius: ff.radius.{size}
     - Shadow: ff.shadow.{size} with DTCG object format
   - Valid vs invalid examples table (3-4 rows each)
8. "What's NOT Tokenized" section (discretion: include for confusion prevention):
   - Component-specific z-index values
   - CSS animation keyframes
   - One-off layout measurements
   - Computed values requiring runtime context
   - SCSS map functions (map-merge, map-get)
9. Maintenance Tasks section:
   - Adding a new token (step-by-step with DTCG format example)
   - Updating an existing token
   - Debugging failed builds (JSON syntax, broken references, invalid $type)
   - Re-running extraction scripts
10. Adopting Tokens in Components section (discretion: brief, prevents scope creep):
    - Before/after example: hardcoded color → CSS variable reference
    - Point to gap-analysis.json for finding hardcoded values to replace
    - Keep to 50-80 lines max
11. References section: W3C DTCG spec, Token Studio docs, Style Dictionary docs, project dtcg-spec.md

Pull real values from tokens/core.json, tokens/semantic.json, and tokens/audit/dtcg-spec.md for all examples. Do NOT use placeholder data.
