  <action>
Create `tokens/audit/component-token-reference-map.md` with these sections:

**1. Button Token Reference Map** — For each button variant (primary, secondary, outline, danger) and each interactive state (default, hover, active, focus, disabled), trace every CSS property to its v1.0 token:

Format per entry:
```
| CSS Property | SCSS Variable | CSS Custom Property | Core Token | Semantic Token |
```

Source data is in 05-RESEARCH.md "Button -> v1.0 Token Reference Map" section. Read the actual SCSS files to fill any gaps in the research data. Trace through TWO indirection layers:
- Layer 1: SCSS variable (e.g. `$color-primary`) defined in button SCSS
- Layer 2: CSS custom property (e.g. `var(--primary-dark)`) that the SCSS var resolves to
- Layer 3: Core token value (e.g. `ff.color.primary-dark`)

For shared/static properties (border-radius, transition), note them separately as state-independent.

**Key finding to document:** The "error" variant in SCSS maps to `ff.color.orange-100` (orange), while "danger" maps to `ff.color.red-100` (red) via `color.bootstrap-danger`. Document this explicitly as the v2.0 component tokens will use correct semantic names (danger = red).

**2. Form Token Reference Map** — Same format for text input and checkbox:
- Text input: trace properties from `_textInput.scss`
- Checkbox: trace from `_checkbox.scss` (note: uses hardcoded hex values, not CSS var references)

For checkbox, document the `#8969f2` gap — no exact core token match exists. Recommend referencing nearest semantic color (`color.action.primary` or new `color.action.primary-selected`). Do NOT add new values to core.json.

**3. New Semantic Tokens Needed** — List all semantic tokens that must be added to `semantic.json` to support component references. Use research data:
- `color.action.primary-border` -> `{ff.color.primary-dark}`
- `color.action.secondary-border` -> `{ff.color.gray-x-light}`
- `color.action.danger` -> `{ff.color.orange-100}`
- `color.feedback.error` -> `{ff.color.red-100}`
- `color.feedback.warning` -> `{ff.color.yellow-100}`
- `color.background.surface` -> `{ff.color.white-200}`
- `color.text.default` -> `{ff.color.gray-darkest}`

Include rationale for each: why a semantic layer adds value (intent-based naming, shared across components).

**4. Reference Depth Policy** — Document the max 3-level depth policy per user decision:
- Rule: component -> semantic -> core (max 3 levels)
- Rule: skip semantic when it adds no value (component -> core directly, max 2 levels)
- Rule: when multiple components share a value, use a shared semantic token (don't have independent core references)
- Include concrete examples of both 2-level and 3-level chains using real token paths from the audit
- Example 3-level: `button.primary.border-color` -> `{color.action.primary-border}` -> `{ff.color.primary-dark}` -> `#B8ABFF`
- Example 2-level: `button.border-radius` -> `{radius.button.default}` -> `{ff.radius.pill}` -> `1.5625rem`

**5. Form Element Scope Decision** (Claude's Discretion) — Document scoping for v2.0:
- Cover text input (primary form element) and checkbox (selection control)
- Skip select/textarea/radio for v2.0 to stay under ~75 token limit
- Rationale: prove the pattern with two representative form elements, expand in v3.0

**6. Static Property Token Decision** (Claude's Discretion) — Document which non-state-changing properties get component tokens:
- Include: font-size, font-weight (useful for component completeness, referenced by both buttons and forms)
- Exclude: border-width (1px is a dimension primitive, not semantic)
- Rationale for each

Create `tokens/audit/unused-core-tokens.md` tracking which of the 160 core.json tokens are NOT referenced by any component token (button or form).

**Process:**
1. Read `tokens/core.json` and list all 160 token paths
2. Cross-reference against the component token reference map (from Task 1) and existing `semantic.json` references
3. A token is "used" if it appears in: the button reference map, the form reference map, or semantic.json `$value` references
4. A token is "unused" if none of the above reference it

**Document structure:**
```markdown
# Unused Core Tokens

Status: v2.0 audit (buttons & forms only)
Total core tokens: 160
Referenced by components: N
Referenced by semantic only: M
Unreferenced: X

## Unreferenced Tokens

| Token Path | Category | Value | Notes |
|------------|----------|-------|-------|

## Notes
- These tokens may be used directly in SCSS without the token system
- Pruning is deferred per user decision (keep core.json complete)
- Future component expansions (nav, tables, modals) may reference some of these
```

Per user decision: use a separate document approach (not inline annotations in core.json) to keep core.json as pure DTCG. This is the "flag unused tokens" approach from Claude's Discretion.
