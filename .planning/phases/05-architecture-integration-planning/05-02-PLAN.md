  <action>
Create `tokens/audit/naming-convention.md` documenting the component token naming convention.

**Sections:**

**1. Segment Order** — Document the locked decision: `component.variant.state.property`
- Component: `button`, `form` (or more specific: `input`, `checkbox`)
- Variant: `primary`, `secondary`, `outline`, `danger` (buttons); `text`, `checkbox` (forms)
- State: `hover`, `active`, `focus`, `disabled` (omitted for default)
- Property: `background`, `border-color`, `color`, `shadow`

Provide a complete enumeration table showing all valid segment combinations for buttons (4 variants x 5 states x 4 properties = up to 80 tokens, but reduced by shared/static properties and default omission).

**2. Default State Omission Rule** — Per locked decision:
- `button.primary.background` = default state (no state segment)
- `button.primary.hover.background` = hover state (state segment present)
- Rationale: reduces token count, default is the most common reference

Provide 5+ examples showing default vs. explicit state:
```
button.primary.background          (default - no state)
button.primary.hover.background    (hover)
button.primary.active.background   (active)
button.primary.focus.background    (focus)
button.primary.disabled.background (disabled)
```

**3. CSS Custom Property Mapping** — Per locked decision:
- Dot path maps directly to CSS var: `button.primary.hover.background` -> `--ff-button-primary-hover-background`
- The existing `name/css/ff-prefix` transform handles this automatically (prepends `ff` if not already present, joins with hyphens)
- No abbreviations in generated CSS vars

Show the complete transform chain:
```
JSON path:   ["button", "primary", "hover", "background"]
Transform:   prepend "ff" -> ["ff", "button", "primary", "hover", "background"]
Join:        "ff-button-primary-hover-background"
CSS output:  --ff-button-primary-hover-background
```

**4. Shared/Static Property Naming** — Per locked decision:
- Properties that don't change across states omit the state segment entirely
- `button.primary.border-radius` (shared across all states of primary)
- `button.font-size` (shared across all variants AND states — omit variant too)
- Provide examples of each level of sharing:
  - Per-variant static: `button.primary.border-radius`
  - Per-component static: `button.font-size`, `button.font-weight`

**5. Token Type Handling** — Document how `$type` works in component token groups:
- Do NOT declare `$type` at variant group level (mixed types within a group)
- Declare `$type` on each leaf token explicitly
- Color tokens: `$type: "color"`
- Shadow tokens: `$type: "shadow"`
- Dimension tokens: `$type: "dimension"` (border-radius, font-size)
- Font-weight tokens: `$type: "fontWeight"`
- Anti-pattern: `$type: "color"` at group level causes shadow tokens to inherit wrong type

**6. Anti-patterns** — List naming patterns that are NOT allowed:
- `button.primary.default.background` (default should be omitted)
- `button.primary.hover.border-radius` (static property should not have state)
- `btn.pri.bg` (no abbreviations)
- `button-primary-background` (use dots in JSON, hyphens only in CSS output)
- `color.button.primary-border` in semantic.json (component-scoped semantic tokens defeat sharing purpose)

Create `tokens/components.json` as a minimal but representative stub that validates the architecture against the existing Style Dictionary build pipeline.

**Stub content requirements:**
- Include ONE complete button variant (primary) with:
  - Default state: background, border-color, color (each with explicit `$type`)
  - One non-default state (hover): background, border-color, shadow (with correct `$type` per token)
  - One shared/static property: border-radius (`$type: "dimension"`)
- Include ONE form element placeholder (input) with:
  - Default state: background, border-color, color (each with explicit `$type`)
- Every `$value` MUST use reference syntax pointing to existing semantic.json or core.json tokens
  - For semantic tokens that don't exist yet, reference existing ones as placeholders (e.g. use `{color.action.primary}` instead of not-yet-created `{color.action.primary-border}`)
  - Add `$description` noting "placeholder - will reference {actual token} after semantic.json is extended"
- Follow W3C DTCG format exactly as existing token files do

**Structure:**
```json
{
  "button": {
    "primary": {
      "background": { "$type": "color", "$value": "...", "$description": "..." },
      "border-color": { "$type": "color", "$value": "...", "$description": "..." },
      "color": { "$type": "color", "$value": "...", "$description": "..." },
      "border-radius": { "$type": "dimension", "$value": "{radius.button.default}", "$description": "..." },
      "hover": {
        "background": { "$type": "color", "$value": "...", "$description": "..." },
        "border-color": { "$type": "color", "$value": "...", "$description": "..." },
        "shadow": { "$type": "shadow", "$value": "{shadow.button.primary}", "$description": "..." }
      }
    }
  },
  "input": {
    "text": {
      "background": { "$type": "color", "$value": "...", "$description": "..." },
      "border-color": { "$type": "color", "$value": "...", "$description": "..." },
      "color": { "$type": "color", "$value": "...", "$description": "..." }
    }
  }
}
```

**Validation steps (run these after creating the file):**
1. Verify JSON is valid: `node -e "JSON.parse(require('fs').readFileSync('tokens/components.json', 'utf8')); console.log('Valid JSON')"`
2. Verify no top-level key collision with core.json (top-level key is `ff`) or semantic.json (top-level keys: `color`, `spacing`, `radius`, `shadow`, `duration`). The keys `button` and `input` must not exist in either file.
3. Attempt a dry-run build: temporarily add components.json to the Style Dictionary source array and run the build to verify reference resolution works. If the build fails due to references to not-yet-created semantic tokens, note which references need placeholder values and update accordingly.

**IMPORTANT:** This is a stub for architecture validation only. Phase 6 will replace it with the full button token set. The stub proves:
- The naming convention produces correct CSS custom properties
- The reference chain resolves across 3 source files
- The `$type` handling works without inheritance conflicts
- Top-level keys don't collide with existing token files
